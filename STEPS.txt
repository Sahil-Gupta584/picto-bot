  FINDINGS
  1. The SDK enforces plan membership CLIENT-SIDE, before any network call:
       invoke() throws IntentMismatchException when the action is not a step in
       the plan recorded by capturePlan(). "An action not in the plan" is a hard
       block that never reaches the proxy. That is our intent_drift gate.
  2. The SDK is fail-closed on proofs: it refuses to invoke without a CSRG
       Merkle inclusion proof, even if the proxy would accept it.
  3. Per-token policy is NOT being honoured yet. Passing
       {rules:[{id, action:'require_approval'|'deny', tool:'push_main'}]}
       returned policyValidation.matched_policies = [] and allowed_tools =
       ['push_main'] - i.e. the rule did not match. Most likely the backend can
       only match tools it knows about, which requires the MCP to be registered.
       RE-TEST IMMEDIATELY AFTER (2). Until then the Slack/HOLD design rests on
       an unverified assumption - do not build on it blind.
  4. ArmorIQ's own source states params are NOT bound to the signed plan:
       "this binds the action but NOT the call params; binding params requires
       the CSRG-IAP Merkle leaf granularity to include args ... (#92)".
       This is authoritative evidence for the README threat model. Use it.

  Deliveries are claimed in SQLite, so the dedupe survives a restart - an
  in-memory set would re-run after a redeploy.

  BUG FOUND AND FIXED WHILE TESTING 3.1:
  Octokit's webhooks.verify() ANSWERS true/false; it does not throw. Our
  verifyWebhook was documented as "throws if the signature does not match" and
  simply returned that value. So every caller that guarded with try/catch - the
  obvious way to use a throwing function - ACCEPTED a forged payload. It is now
  fail-closed: anything that is not exactly true throws. This is exactly why the
  probe signs its own requests and asserts the REJECTIONS; a hand-written curl
  would have passed.

  CONTEXT FIX (the issue-comment trap the user caught):
  An issue_comment payload carries the comment plus a STUB of the issue - no
  body, none of the earlier comments. Building a run from the payload alone
  leaves the agent acting on "please do that" with no idea what "that" is.
  So the context is fetched instead:
    - title + body   always, every run. It is the spec, and it is short.
    - comments       all of them on first contact; afterwards only the ones
                     this session has not been shown
                     (cursor in sessions.last_comment_id)
  The webhook and run-local.js call the SAME builder, so the terminal driver
  cannot quietly be kinder to the agent than production is.

STATUS: run-local.js, the webhook and the Slack approval all work. What still
stands between us and the demo is ArmorIQ MCP registration (USER ACTION #2),
without which an allowed action cannot actually execute, and the Slack signing
secret (USER ACTION #3).

  role/amount-shaped (requesterRole, requesterLimit, domain, amount) - it is for
  spend approvals. Ours is "may this one tool call proceed", and the decision and
  its audit trail live in our own store, which is also what lets a Slack button
  still be recorded after the process that asked has restarted.

  FAIL-CLOSED TWICE OVER: if Slack is unreachable the run still stops - we never
  continue because we could not ask. And a decision is refused if one already
  exists, so a replayed callback cannot flip a denial into an approval.

SENIOR NOTES
================================================================================
  1. ArmorIQ matches tool NAMES, not arguments. Anything behind run_command
     inherits run_command's permission - you cannot block a single command
     inside it. This is why push_main is a separate tool from push_branch, and
     why irreversible operations must each get their own name.

  2. Policy semantics:
       deny              -> absolute DENY, no approval path, ever
       require_approval  -> HOLD; the only path a human can approve.
     The Slack flow requires require_approval, not deny. UNVERIFIED (finding 3).

  3. The maintainer's comment asks for the change to land on main with no PR.
     A compliant agent therefore WILL attempt push_main - the attempt is
     deterministic, not a lucky roll of the model.

  4. run_command executes on the host. Isolation is a directory, a cwd jail, a
     timeout and an env allowlist - not a VM. Real isolation needs a container.
     Known limitation, documented, not hidden.

  5. Never run the agent against a developer's own working tree. Clone per run,
     always. C:\s\opencmo is dirty (feature branch, untracked files).

  6. tunnel currently: https://bd87-106-194-232-113.ngrok-free.app -> :8787
     Free ngrok URLs change on restart. Re-register in ArmorIQ and update
     armoriq.yaml whenever it does.
